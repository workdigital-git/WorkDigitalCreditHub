- Many Users ↔ Many Organizations (Memberships)
- Credits are owned/burned against an Organization Wallet
- Users can create orgs and add users to orgs
- MUST NOT BREAK any existing API or the current single-user flows.

CORE COMPATIBILITY RULES (NON-NEGOTIABLE)
1) Existing endpoints MUST keep working with ZERO client changes.
2) Existing single-user credits MUST remain available and burnable as before.
3) New multi-org functionality MUST be additive:
   - Prefer new endpoints under /api/v2/*
   - Or extend responses with optional fields but do not change required fields or semantics.
4) For legacy clients, treat each user as having an implicit “Personal Organization” and “Personal Wallet”.
5) All credit burns must remain idempotent and auditable.

PHASE 1 — DATABASE SCHEMA (ADD ONLY, NO DESTRUCTIVE CHANGES)
Create migrations for:

TABLE organizations
- id (uuid pk)
- name (text, not null)
- created_by_user_id (uuid, not null)
- created_at (timestamp)
- updated_at (timestamp)

TABLE organization_memberships
- id (uuid pk)
- organization_id (uuid fk -> organizations.id)
- user_id (uuid fk -> users.id)
- role (text: OWNER|ADMIN|MEMBER)
- status (text: ACTIVE|INVITED|SUSPENDED)
- created_at, updated_at
Unique constraint: (organization_id, user_id)

TABLE wallets
- id (uuid pk)
- organization_id (uuid fk -> organizations.id)
- type (text: CREDITS)
- status (text: ACTIVE|SUSPENDED)
- created_at, updated_at
Unique constraint: (organization_id, type)

OPTIONAL (preferred if ledger doesn’t exist already):
TABLE credit_ledger
- id (uuid pk)
- wallet_id (uuid fk -> wallets.id)
- direction (text: CREDIT|DEBIT)
- amount (integer, not null)
- product (text, not null)  // e.g. "CREDITHUB", "RECEIPTS"
- feature (text, nullable)  // e.g. "OCR"
- external_ref (text, not null) // idempotency key
- performed_by_user_id (uuid, nullable)
- metadata_json (jsonb, nullable)
- created_at (timestamp)
Unique constraint: (wallet_id, external_ref)

PERSONAL ORG + WALLET BACKFILL
Write a migration/script that:
- For every existing user:
  - Create an org: "<email> Personal" or "<user_id> Personal"
  - Create OWNER membership
  - Create wallet
- Map legacy user credit balance into this wallet:
  - If legacy model stores a balance number, seed a CREDIT ledger entry equal to that balance
  - If legacy model is already ledger-based, just associate wallet_id for that user’s personal org (see Phase 2 shim)

IMPORTANT: If there is already a credits table keyed by user_id, DO NOT REMOVE IT.
We will keep it for legacy compatibility, but v2 will primarily operate on wallets.

PHASE 2 — SERVICE LAYER (TENANCY + COMPATIBILITY SHIM)
Implement a tenancy service module, e.g. server/services/tenancy.ts:

Functions:
- getOrCreatePersonalOrg(userId): returns org + wallet
- listUserOrgs(userId): returns orgs + membership role/status + wallet_id
- assertUserInOrg(userId, orgId): throws 403 if not ACTIVE
- createOrg(userId, name): creates org + OWNER membership + wallet
- inviteUserToOrg(inviterUserId, orgId, emailOrUserId, role): creates INVITED membership (if user exists) or stores pending invite (see below)
- acceptInvite(userId, orgId): sets membership to ACTIVE if INVITED
- addUserToOrg(adminUserId, orgId, targetUserId, role): sets ACTIVE membership directly (admin/owner only)
- removeUserFromOrg(adminUserId, orgId, targetUserId)

Invites:
- For v1, keep it simple: only allow adding existing users by user_id or email lookup.
- If email doesn’t exist, return a clear error (“user not found”) for now.
- Later we can add pending invites table; scaffold interface but don’t overbuild.

COMPATIBILITY SHIM FOR LEGACY CREDIT OPERATIONS
Create a wrapper around existing credit burn/add functions so that:
- If endpoint is legacy (/api/* existing):
  - Resolve wallet via getOrCreatePersonalOrg(userId)
  - Perform the credit operation against wallet (and also keep legacy storage in sync if needed)
- If endpoint is v2 and includes orgId/walletId:
  - Validate membership, then operate on that wallet

Key: legacy semantics must be identical (same approvals/declines, same balance changes).
If legacy response returns “balance”, keep returning “balance” as before.

PHASE 3 — API ENDPOINTS (ADD V2; KEEP V1 UNCHANGED)
Add new endpoints under /api/v2:

Auth required for all.

GET /api/v2/me/orgs
Response:
{
  "orgs": [
    {
      "org_id": "...",
      "name": "...",
      "role": "OWNER",
      "status": "ACTIVE",
      "wallet_id": "..."
    }
  ],
  "default_org_id": "... (optional)"
}

POST /api/v2/orgs
Body: { "name": "Acme Inc" }
Response: { "org_id": "...", "wallet_id": "...", "name": "...", "role": "OWNER" }

POST /api/v2/orgs/:orgId/users
Body: { "target_user_id": "...", "role": "ADMIN" }
Response: { "ok": true }

(OPTIONAL but useful)
POST /api/v2/orgs/:orgId/users/by-email
Body: { "email": "user@acme.com", "role": "MEMBER" }
Response: { "ok": true } or { "error": "USER_NOT_FOUND" }

DELETE /api/v2/orgs/:orgId/users/:userId
Response: { "ok": true }

GET /api/v2/orgs/:orgId
Response: { "org_id": "...", "name": "...", "members": [...] } (only owner/admin)

CREDITS V2
POST /api/v2/credits/burn
Body:
{
  "org_id": "...",            // required unless wallet_id provided

  "product": "RECEIPTS",
  "feature": "OCR",
  "external_ref": "receipts:receipt_123:ocr:v1",
  "metadata": { "receipt_id": "receipt_123", "job_id": "job_77" }
}
Response:
{
  "approved": true,
  "balance": 1234,
  "ledger_id": "..."
}

GET /api/v2/wallets/:walletId/ledger?limit=50
Response: { "items": [...] }
